# Upgrade to Umbraco 19

From `18.0.0` (backoffice `18.0.0`, `[18.0.0, 19.0.0)` range) to `19.0.0-beta1` (tag `release-19.0.0-beta1`).
Branch `v7/dev`, cut from `origin/v6/dev` (package `6.3.0-alpha`). Worktree: `../BlockPreview-v7`.

**Targets CMS release:** `release-19.0.0-beta1`. The package ships as `7.0.0-beta1` (pre-release) until the final 19.0.0.

Status: **plan approved 2026-11-10. Inventory is partial** (see "Still to verify").

## Decisions

- 2026-11-10: base the new line on `origin/v6/dev` as `v7/dev`, in a worktree; target `19.0.0-beta1`.
- Open: `PackageValidationBaselineVersion` is `6.0.0`; for a new major the baseline should move (no baseline until `7.0.0` ships).
- 2026-11-10: external (Library) element blocks are rendered like local blocks via the CMS element service.
- 2026-11-10: runtime async is not opted into for the package (optional, no consumer impact); decide again at the RC.
- 2026-11-10: `BlockDataConverter` passed `owningPropertyCulture: null` to `ConvertToElement` as a stopgap; the behaviour task replaced it (see below).
- 2026-11-10: external elements are fetched with `IElementCacheService.GetByKeyAsync(key, preview: true)`, the service CMS's `BlockPropertyValueCreatorBase` uses for `IsExternalContent` layout items, but only through the package's own `IExternalElementResolver` seam (see the auth decision). `IPublishedElementCache` is the lower-level cache behind it; `IBlockElementService` only builds elements from local `BlockItemData`, so it does not apply. Preview renders the draft, never the published version. A missing element is logged and shows the package's error alert (in a grid area the child is skipped, as for an orphaned layout item). Settings of an external block stay local (`SettingsData` by `SettingsKey`), as in the CMS.
- 2026-11-10: owner for area/nested blocks stays the page. Verified at `release-19.0.0-beta1:BlockPropertyValueCreatorBase`: every layout item, including grid area children, is converted with the property's owner; only block editors nested inside an element get that element as owner, and the CMS's own converters do that when the element's properties render. No change made.
- 2026-11-10: `owningPropertyCulture` follows the CMS's `BlockPropertyVariance.OwningPropertyCulture`: the preview culture when the block property's variance narrowed by its owner's varies by culture, otherwise `null`. The property is looked up on the page by `blockEditorAlias`; a block editor nested in a block is not a page property and is previewed as invariant (as before).
- 2026-11-10: auth, two parts. (1) Endpoint access: `BlockPreviewApiControllerBase` derives from `ManagementApiControllerBase` (`[Authorize(BackOfficeAccess)]` + `UmbracoFeatureEnabled` in 19) and repeats `BackOfficeAccess`; the 19 policy builds on the cookie and bearer schemes, so the endpoints still require a backoffice user and no attribute change is needed. Not exercised against a running 19 site. (2) **Per-element permission (added after review, security):** the element key comes from the client-supplied layout item, and `IElementCacheService.GetByKeyAsync(preview: true)` only checks browse permission inside a website preview session, which a backoffice request never has, so any backoffice user could read any Library element's draft. `ExternalElementResolver` now calls `IElementPermissionService.AuthorizeAccessAsync(user, key, ActionElementBrowse.ActionLetter)` for the user from `IBackOfficeSecurityAccessor` (as `ByKeyElementController` and `BatchElementsController` do at `release-19.0.0-beta1`) before it reads the element. No user or a non-success status gives `NotPermitted` (the element is never read, no published fallback): a "not permitted" alert at the top level, and the child is skipped in a grid area (as the CMS batch endpoint omits unauthorized ids). An unknown key is `NotFound`.
- 2026-11-10: SDK 11 generates `buildTransitive/<PackageId>.targets` for static web assets, so the package's own build file is now `buildTransitive/Umbraco.Community.BlockPreview.props` and NU5118 is a build error. Don't name a hand-written file `<PackageId>.targets`.

## Breaking changes for consumers

Task 1 removed the package's own `[Obsolete(... "Scheduled for removal in v7.")]` members (public API; `PackageValidation` CP0002 against baseline 6.0.0 lists them). More may follow from CMS-forced signature changes found at compile.

- `BlockTypeSettings.Stylesheet` (use `Stylesheets`); the `"Stylesheet"` appsettings key no longer binds.
- `Constants.CacheKeys.BlockType`.
- `BlockPreviewApiController`: both obsolete constructors (without `IEntityService`; without `IBlockPreviewResponseEnricher`), and the actions `GetGridStylesheet`, `GetListStylesheet`, `GetRteStylesheet` (endpoints `GET preview/{grid|list|rte}/stylesheet`; use the `.../stylesheets` endpoints).
- `BlockPreviewService`: both obsolete constructors (the 19-parameter and the `ITypeFinder` one), `RenderRichTextBlock(blockData, content, controllerContext, blockEditorAlias, documentTypeUnique)`, `GetStylesheetPath(...)` and the protected virtual `CreateViewData(...)` (override `CreateViewDataAsync`, which no longer calls it).
- `IBlockPreviewService`: `RenderRichTextBlock(..., blockEditorAlias, documentTypeUnique)` and `GetStylesheetPath(...)` removed. The default implementations of the 3-argument `RenderRichTextBlock` and `GetStylesheetPaths` went with them, so they are now abstract: external implementers must implement both.
- `BlockViewRenderer`: constructor without `IServiceScopeFactory`/`ILogger`.
- `BlockPreviewViewResolver`: constructor taking `IWebHostEnvironment`.
- `DataTypeSavedNotificationHandler(AppCaches)` and `ContentTypeSavedNotificationHandler(AppCaches)` constructors.
- Generated client: `BlockPreviewService.getGridStylesheet/getListStylesheet/getRteStylesheet` and their types; `stylesheet` field on `BlockTypeSettings`.

Behaviour task (public API, all additive; `IBlockDataConverter`/`IBlockPreviewService` additions have default implementations marked `TODO (v8)`):

- `IBlockDataConverter.ConvertToElement(data, owner, owningPropertyCulture)`. An implementer that does nothing keeps the old behaviour (culture ignored).
- `IBlockPreviewService.RenderGridBlock/RenderListBlock/RenderSingleBlock/RenderRichTextBlock` overloads taking a `BlockRenderOptions` (new public sealed class: `LayoutKey`, `OwningPropertyCulture`) after `controllerContext`. The old overloads stay and forward with empty options. A custom `IBlockPreviewService` only sees the new calls through its default implementations, which ignore the options, so it must implement the new overloads to get layout-key and culture handling. **Source break:** a call that passes a literal `null` as the 4th argument (previously `blockEditorAlias`) is now ambiguous (CS0121); pass `blockEditorAlias: null`/a string or name the argument.
- New public `IExternalElementResolver` (`ResolveAsync(elementKey)` returning `ExternalElementResult` with `ExternalElementStatus`) with the internal default `ExternalElementResolver`, registered by the composer as a singleton. `BlockPreviewService` has a **new** constructor taking it as a tenth parameter (`[ActivatorUtilitiesConstructor]`; the composer registers the service through `ActivatorUtilities`). The old nine-parameter constructor is `[Obsolete]` and resolves the resolver through `StaticServiceProvider`. Scheduled for removal in v9. A subclass calling `base(...)` with the old arguments gets CS0618 until it adds the resolver; `docs/advanced-customization.md` shows the new call.
- **Behaviour change:** culture-variant blocks now preview in the request's culture (the controller's `currentCulture`) when the block property varies by culture; before, they always rendered in the default culture (the `ConvertToElement` stopgap passed `null`).
- `BlockPreviewApiController`: `PreviewGridBlock/PreviewListBlock/PreviewSingleBlock/PreviewRichTextMarkup` gained a trailing optional `Guid? layoutKey` (new optional query parameter on the endpoints). Binary signature of these action methods changed; they are HTTP actions, not a supported C# API. The OpenAPI client (`types.gen.ts`) needs regenerating.
- Private members changed (only tests reflect on them): `ConfigureBlockInstanceAreas` is now `ConfigureBlockInstanceAreasAsync`, and `GetMatchingGridLayout` takes the layout item `FindLayoutItem` already found (optional; it falls back to the first item with the block's content key).

Frontend task:

- The package's backoffice client needs Umbraco 19 (`@umbraco-cms/backoffice` 19.0.0-beta1): it relies on the 19 layout-key/Library block model (`key` and `isExternalContent` on layout items) and the 19 types. Block custom views read the block's layout item `key` from the entry context's `layout`.
- `blockIndex` (query parameter, and `ViewData["blockIndex"]` in views) is now the block's position in the layout, for every block. It used to be the position in the manager's content data, which Library blocks lack (they got -1 or undefined). A root block gets its place in the manager's layouts, an area child its place within its parent area, and a block not yet in the layouts gets 0. A view that used `blockIndex` for a Library block now sees a valid index; local blocks keep the same index unless content and layout order differ.
- The `token()` bearer callback is gone from the client config; calls authenticate with the backoffice cookie (`credentials: 'include'`).
- Generated client: `PreviewGridBlockData/PreviewListBlockData/PreviewSingleBlockData/PreviewRichTextMarkupData` `query` gained optional `layoutKey`.
- Exported `BlockPreviewQuery` and `RtePreviewQuery` (`src/repository`) gained optional `layoutKey`; `BlockContext` gained `layoutKey` and `isExternalContent` (required fields, so code that builds a `BlockContext` literal must add them).

## Follow-ups

- **Known limitation on CMS 19.0.0-beta1: a Library element inside a Block Grid area is lost by the CMS itself** (root cause proven in the grid-area investigation, see Log). `UmbBlockGridEntryContext`'s 'Secure areas fits options' observer (`block-grid-entry.context.ts` ~L220) compares `blockType.areas ?? []` with the layout areas; a Library block's block type resolves asynchronously, so for a moment `areas` is `[]` and the observer rewrites the layout as `items: []`, which is saved. The package cannot recover it. Upstream fix validated by route-patching: read `this._blockType.asObservablePart(x => x?.areas)` (undefined until the block type resolves; the existing `!areas` guard skips it). Not yet reported upstream; re-test on the next 19 pre-release. The seed `Library Test` page keeps the area child in the committed uSync data; saving that page on beta1 strips it.

- Frontend task: send `layoutKey` (the block's layout item `key`, from `context.layouts`/the block entry context) as a new query parameter on `preview/grid|list|single|rte`, and filter the `layout` it sends by layout key instead of `contentKey` (the list/single elements filter `layouts` by `contentKey`, which returns every instance of a reused element). For a Library block the manager's `contents` has no entry for the key, so `contentData` is empty while `layout` carries `isExternalContent: true`; do not skip the preview when `contentData` is empty and the layout item is external. `validatePreviewData` and the `contents?.indexOf(...)` for `blockIndex` need the same care. Regenerate the client for the new query parameter.
- Frontend task, done on the client side, not run against a live 19 site: `layoutKey` is sent on all four preview calls and `layout` is filtered by layout key; `src/api/types.gen.ts` was hand-edited for `layoutKey` (no .NET 11 SDK, so no site to `npm run generate` against; `openapi-ts` 0.99.0 has not regenerated `src/api`, so regenerate once a 19 site runs and check the diff is only `layoutKey` plus generator churn). The package does not call block manager/entries delete methods, Tiptap `setBlock` or parse RTE `data-key`, so nothing there needed adapting. Smoke: Library block (Block List, Grid, Single, RTE) previews, the same Library element used twice in one property (each preview must show its own instance), `Authorization` header absent and cookie auth working on `preview/*` calls.
- Smoke: session expiry while previews are on screen. `configureClient` only retries GET requests after a 401 (`api-interceptor.controller.ts`), so POST previews are not retried; expect one "Some actions were not completed" warning and previews that stay as they were until the editor signs in again.
- `@umbraco-cms/backoffice` 19 ships `umbraco-package-schema.json` with a generator bug (`"type": "{boolean}"` on 15 `additionalOptions` properties) that makes strict validators reject the schema. The package's manifests validate once that literal is read as `boolean`.

- Pre-existing, not fixed: `BlockPreviewApiController.GetPublishedContent` (~line 548, `context.Content?.GetById(preview: true, nodeKey)`) loads any document's draft by the client-supplied `nodeKey` without checking the user's document permissions, so a backoffice user can render previews against a page they cannot browse. The CMS guards documents with `IContentPermissionService`/`ContentPermissionResource`; needs its own fix (decide the fail behaviour for unsaved pages first).

When a block's Razor view renders a nested Block List/Grid property, the CMS's `BlockPropertyValueCreatorBase` calls `IElementCacheService.GetByKeyAsync(layout.ContentKey, preview)` for nested external layout items with no permission check (document drafts via content pickers behave the same). One fix for the whole class could be `IPreviewSessionService.Start()` in the preview controller so `PreviewAccessEvaluator` applies with the current backoffice user, but its denied fallback is the published version; decide whether that is acceptable.
- Optional tightening, not done: the preview endpoints require only `BackOfficeAccess`, while the CMS batch element endpoint also requires `TreeAccessDocumentsOrElementsOrMediaOrMembers`.

- Library child in a Block Grid area, diagnosed (2026-11-11). Root cause is a CMS 19.0.0-beta1 bug, not the package: `UmbBlockGridEntryContext`'s "Secure areas fits options" observer compares `areas` (`blockType.areas ?? []`) with `layoutAreas`. A Library (external) block's block type resolves asynchronously, so for a moment `areas` is `[]` while `layoutAreas` holds the saved area; the lengths differ and the observer rewrites the entry layout as `{ key, items: [] }`. That write flows through `observeThisLayout`, the entries context and `setLayouts` into the manager and the property value, so the child is gone from the client state (and from a Save: the PUT body had `items: []`; uSync then exported the stripped draft). It reproduces with the package's bundle replaced by an empty file, so Block Preview's `#filterLayouts` and the POST body are innocent: they faithfully send what the entry context holds. Local blocks are unaffected because their block type is known synchronously. Backend is fine: with the child put back into the grid POST body, the server emits the area container (`Hero` only emits it when an area has items). The local CMS clone's `origin/main` and `release/19.0` still have the same `areas ?? []`, so it is not fixed upstream yet. Evidence: with that one observer reading `blockType.areas` (undefined until resolved, which the existing `!areas` guard already skips), the manager keeps `[1]`, the page shows 2 `umb-block-grid-entry` and an areas container, and both Library Heroes preview. No package workaround: the wipe runs before the preview view is created and rewrites the value itself, so there is nothing left to recover. To report upstream, with that one-line change. Test data caveat: saving Library Test in the backoffice on beta1 rewrites `uSync/v19/Content/library-test.config` without the child (restore it with `git checkout`).
